# Drafter

A local-first home journal and planner. Five tabs, the same on desktop and phone: **Home · Tasks · Calendar · People · Kitchen** (the phone's bar orders them Home · Calendar · Tasks · Kitchen · People). Home is the day — a briefing strip, today's focus, what's overdue and due, habits and routines, tonight's dinner, the journal — with the week's review a segment away. Projects hold tasks with due dates, priorities, checklists and a comment trail; a timeline lays projects and milestones out over time; bills sit on their due dates. People and places track who you saw and where you went. Kitchen holds recipes, the week's meals (cooked or eaten out) and a grocery list, and those meals show on the calendar too. Cmd/Ctrl+K is a command palette that jumps anywhere, creates anything, searches everything and answers questions from your own planner. Tasks can link to GitHub issues, pull requests, repos or Projects boards and show their live state.

## Run it

```bash
npm install
npm run dev          # app on http://localhost:5173
```

### Modes

**Cloud mode (Supabase)** — active when `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` are set (`.env.local` locally, site env vars on Netlify). The app requires sign-in (Supabase Auth, with no public sign-up: the site owner's own account is made in the Supabase dashboard, and the owner creates the rest in Admin with *Create account* — an email and a temporary password — or *Invite by email*, which copies a one-time invite link) and syncs every change to Postgres. Bots can manage posts through the `bot` gateway, a Supabase Edge Function that takes a `BOT_TOKEN` rather than the service key (documented in the local, unpublished `BOTS.md`); it acts as the site owner and sees only what the owner sees in the app — never another member's journal, reviews, calendar subscriptions, habits or routines. Schema lives in `supabase/migrations/` (`supabase db push` applies it).

**Local mode** — with no Supabase env vars, data stays in the browser (IndexedDB). Useful for offline dev; there is no separate local server anymore.

### Deploying to Netlify

`netlify.toml` is ready: build `npm run check`, publish `dist`, plus an `/api/ai` function that proxies the model server-side (session-gated, so visitors can't burn credits). Set these site environment variables: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, optionally `GITHUB_TOKEN` (see GitHub links), optionally `SUPABASE_SERVICE_KEY` (functions only, never sent to the browser: calendar sync needs it, and so do Household, Admin, push and the morning digest, email-in, server backups and the assistant endpoints, which answer 501 or do nothing without it), optionally `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` and `MICROSOFT_CLIENT_ID` / `MICROSOFT_CLIENT_SECRET` (see Calendar sync), and one AI key for the ✨ features:

- `NVIDIA_API_KEY` — a free key from [build.nvidia.com](https://build.nvidia.com) (NVIDIA Developer Program, ~40 requests/min). Uses the OpenAI-compatible NIM endpoint; pick a model with `NVIDIA_MODEL` (default `nvidia/nemotron-3-super-120b-a12b`; list at `https://integrate.api.nvidia.com/v1/models`).
- `ANTHROPIC_API_KEY` — Claude instead (plus `ANTHROPIC_WORKSPACE_ID` if that key is identity-linked and not scoped to a single workspace; model via `ANTHROPIC_MODEL`).

If both keys are set NVIDIA goes first, and a call it rate-limits or fails (429 or 502) is tried once more on Claude, so the second key works as a backup. `AI_PROVIDER=nvidia|anthropic` picks which goes first: `nvidia` still falls back to Claude when that key is set, `anthropic` never falls back to NVIDIA, and if the key it names is not set the ✨ features are off.

`/api/ai` allows about 30 calls per 10 minutes per account and caps what each call may ask for at 4,096 tokens (a call that goes to Claude is sent with 8,000, since its thinking counts against that number); past the rate limit it answers 429 with *Too many AI requests from this account* and when to try again. The count is kept per warm function instance, so it is a safeguard rather than a quota. Without a valid session `/api/ai` and `/api/github` answer 401, and with the Supabase settings missing from the host they answer 503 rather than serving anyone.

## Model

- **Project** — a container with a name, color, status (active / paused / done / archived), optional start and target dates, milestones, and an optional GitHub repo or Projects URL (a Projects board can sync status and due dates both ways).
- **Task** — title, a description (links, notes and a GitHub URL all live in it), status (Wishlist → To do → Doing → Done, and Blocked while it waits on another task; leftover Canceled tasks still display), priority (low / normal / high / urgent), due date, tags, a checklist (on a saved task a step is written as you add, tick, rename or remove it, not on Save), a timestamped comment trail, images, and recurrence (daily / weekly / biweekly / monthly / quarterly / yearly — completing one spawns the next, on a clamped day so a monthly task due the 31st never skips February).

There is no project bar and no project filter: you are always on your one **home project**, and every view shows everything. Projects still exist as a grouping — a chip on each Board card, a bar on the Timeline, the thing a template or *Draft a plan* creates — and are edited from the Timeline, the Week review, a milestone (◆) in a calendar day, search and, for an active project with a target date, its progress card on Today (the ongoing home project has no card there). A new one comes from the palette (type *New project*; it is not a quick action) or the Timeline's *+ New project* button. **Notes** (a segment of the Tasks tab) is one list: notes of your own — as many as you like, each a page for one subject, pinned ones first — beside the project notepads (see Tasks → Notes for which ones), newest edit first, with a search. *+ New note* starts one (it is saved once it has a title or some text; text alone is an *Untitled note*), the *About* chip ties it to a project, and Delete sends it to Trash with an undo. Each page is one you type straight into, with a formatting bar (bold, italic, underline, strikethrough, headings, lists, checklists, quotes, inline code, code blocks, links, dividers), an emoji picker, and photos pasted, dropped or picked from the 📷 button and shown inline. Notes are stored as a sanitized HTML subset; photos go to the synced media store and are referenced by id. It autosaves as you type. Older Markdown notes convert automatically on first open.

**Templates:** a new project can start from a template (built in: holiday/trip, moving house, party, quarterly finances, room makeover — or any project you've saved with *Save as template*). The Start date anchors every task and milestone. **✨ Draft a plan from a goal** asks the model for dated tasks and milestones from one sentence; review the list, then create the project with it or add it to an existing one. Settings → Data → *Project templates* lists the ones you have saved, each with a two-step *Remove*; the section is hidden until there is one.

**Command palette** (🔍 or Cmd/Ctrl+K) does five things from one box. Empty, it shows *New task* and *New bill*, with *Plan my day* until noon and *Shut down* from 5pm, then your six most recently changed open tasks. Typing matches commands by name and keyword — jump to any view or segment (Home, Week, Journal, Tasks, Board, Bills, Notes, Calendar, People, Places, Kitchen), open Settings, or run **New task / New project / New bill**, **Plan my day**, **Shut down**, **Plan next week** or **Ask Drafter**, the last four opening over whatever you are looking at — beside a search of tasks (with their comments and checklists), your notes, projects (with their notepads), people, places and journal entries; a note opens in Tasks → Notes, and a person has a *Saw … today* button that logs a visit, with undo. Type something new and **Enter** opens a prefilled task editor, where the sentence is read for a date, priority, people, tags and a repeat before you save (a date on its own is filled in at once; anything more is offered for you to apply); it never files the task under a project. **Shift+Enter** (or the row's *Capture* button, the way to do it on a phone, which has no Shift key) captures the line straight to the Inbox with no editor, matching it against your active projects (the offline parse writes instantly, the model's parse merges in afterwards, and the toast says where it landed, with undo). Whatever you type also offers an *Ask Drafter* row: first when the line reads as a question ("when did I last…", or one ending in ?), otherwise straight after *Create task*. On a phone the installed app is a **share target**: share a link or text from any app and it opens as a new task (a URL goes into the description, not the title). To-do tasks with no project and no date stay in Today's **Inbox**, newest first, until they get a project, a date or another status, so nothing captured gets lost.

**In the task editor**, tasks also carry **files** (any type, synced through the media store) and **blocked-by** links: giving a To do task a blocker marks it Blocked, and it moves back to To do by itself when its blockers complete. At the foot of the task editor sit Repeat, then Tags, then Activity (the comment trail), then, on a saved task, **Versions**: its last 20 earlier copies from the server, each with *Restore*, including an edit that lost to a newer one from another device, marked *Lost to a newer edit*. The editor's People picker adds someone new by name when they are not saved yet. On a phone the five tabs sit at the bottom and a right-swipe on a Today row completes it.

**Ask Drafter** answers a question about your own planner ("when did I last see Mum?"), from the palette's row or its command. The matching records are found on the device and listed as sources straight away; one ✨ call then writes the answer, with its sources as chips that open them, and it can only cite records it was sent. The journal is read only when you turn on its chip, which this device remembers; email addresses and phone numbers are masked, and amounts go out only for a question about money. With no assistant available, the sources are still shown.

**Household.** Settings → Household → *Create household*, then add members by their account email. Only the household's owner can add or remove people, and adding someone leaves an invitation in their own Settings → Household, where they choose *Accept* or *Decline*; nothing is shared until they accept (the site owner creates accounts in Admin). Anyone can *Leave*; a removed member's records are reassigned to the household's owner. Each member sets the name the others see. Everyone in the household sees the same projects, tasks, notes and people and can assign tasks (*Who's doing it*); the Tasks tab's segment row gains a **Mine / Everyone** switch that narrows Today, the list and the board alike (Home and Calendar say *Showing only your tasks* while it is on, with the way off). Calendars, reminders, reviews and the journal stay personal. Under the hood every record carries its owner and the database policy grants access to your own records plus your household's, replacing the original single-owner policy; existing data is assigned to the owner on migration. The site owner can delete an account from Admin → Users (two steps): its shared records become the site owner's, and its journal, reviews, calendar subscriptions, habits and routines are deleted with their history. Backup snapshots already taken are left as they are; *Disable* locks someone out without deleting anything.

**Deleting is two-step everywhere:** the first click arms the button, a second click within four seconds confirms. Anything deleted (tasks, projects, notes, people, places, recipes, meals, grocery lists, events, journal entries, reviews, templates, calendars, habits and routines) goes to the **Trash** (the *Trash* button on Tasks → List, inside the *Import / Export* menu on a phone) for 90 days, where one click restores it on every device. A two-step *Delete forever* empties the record and marks it deleted on every device, so a stale copy cannot bring it back (offline, it waits for the next sync and the toast says so); the server drops the empty row after 90 days, and the copy it replaced stays in the version history for up to 60 days. In local mode it is removed from the browser at once. The undo toast still works too.

## Views

Five tabs, on desktop and phone alike: **Home · Tasks · Calendar · People · Kitchen** (the phone's bar orders them Home · Calendar · Tasks · Kitchen · People). A tab that has more than one way of looking at its data holds those as **segments** in a row under the tab bar rather than as more tabs — there is no More drawer. Home holds Today / Week / Journal, Tasks holds List / Board / Bills / Notes, Calendar holds Month / Week / Timeline, People holds People / Places. Tasks, People and Calendar remember the segment you last chose, and Kitchen keeps its own Recipes / This week / Grocery row, remembered the same way; tapping Home always returns to Today. Old deep links still land: `?view=board|bills|notes` open the Tasks tab on that segment, `?view=today|review` open Home on the day or the week. `?plan=day`, `?plan=shutdown` and `?plan=week` open Plan my day, Shut down or Plan next week — over Home, or Home → Week for the last, unless the link names a view. A plan link writes nothing (the sheet waits for its own button), and a task, capture or journal line in the same link is ignored.

- **Home → Today** — a **briefing strip** first: a greeting for the hour — by first name when the account has one — then the day's one action (**Plan my day** or **Shut down**, below) and a tile for each fact the day has — the weather, today's work mode and hours, events (with the first start time), habits done of due, tonight's dinner. Weather is opt-in and comes from Open-Meteo with no key. One picker on the strip offers *Off*, *Use my location*, or a **major city** (Phoenix, London, Tokyo…): pick a city and nothing about where you are is ever asked for — only that city's public coordinates go to Open-Meteo. *Use my location* is the only choice that prompts for permission; either way nothing is stored server-side, and *Off* forgets the location, the city and the forecast. A US city (or a device set to English (US) with its own location) reads in °F, everywhere else in °C. Directly under the strip, **Today's focus** lists the tasks picked for today — in Plan my day, in last night's Shut down, or by an assistant — up to three, open ones first, with how many are done and each task's time block; *Edit* opens Plan my day at the focus step, and deferring a task from the card also takes it out of today's focus. The lists below leave those tasks out and say how many are in today's focus instead (the count tiles still include them). In a household, each person's focus is their own. On a clear day (no events, nothing due or overdue) a short **from your wishlist** card follows, so spare time has somewhere to go. Below that: count tiles for overdue, due today and open — plus this week and done this week on a wider screen — where overdue, due today and this week jump to their lists, and one button to push everything overdue to tomorrow; then overdue, due today, this week, in progress with no date, blocked, the Inbox, going stale (to-dos with no date untouched for over 14 days), Next up, this week's Top 3, tonight's dinner, stalled projects and progress for active projects with a target date, people due a catch-up and places due a return, upcoming birthdays and anniversaries, what's coming up on your calendars in the next 14 days, what you finished in the last 7, and (on Sunday) last week's review excerpt; one-tap complete and defer.
- **Home → Today: Lunch & dinner ideas** — when lunch or dinner has nothing planned, a card below the count tiles (and below tonight's dinner, when there is one) and above the task lists offers a few for each, titled *Lunch ideas* or *Dinner ideas* when only one is empty — what you have most, and old favourites you haven't had for longest, from the recipes you cook and the places you eat at — each with its reason. A tap plans it for today, with an undo. Lunch ideas go at 2pm and dinner ideas at 8pm, and *Not today* hides the card on this device until tomorrow.
- **Home → Today: Plan my day and Shut down** — the strip's first tile is **Plan my day** until 5pm (until 8pm while nothing is in focus), then **Shut down** (from 5pm once a focus is set, from 8pm either way), and *Day closed* once this device has shut the day down — a note kept on this device only; tapping it opens Shut down again. Both are in the command palette too. **Plan my day** takes up to four steps: anything overdue gets a new day (today, tomorrow, next week, back to the wishlist, or done); up to three tasks become today's focus, from what was carried over, what is due today, this week's 3 and Next up, or a new task typed in; each can have a block of 30 minutes, an hour or an hour and a half in the day's free stretches between 8am and 9:30pm, saved as an event (so busy wherever your events are mirrored); and an empty lunch or dinner can be decided from its ideas. Nothing is written until *Done*, and one Undo takes it all back. **Shut down** has the evening routines to tick, today's journal line (the same entry as Today's card), what is left over — your unfinished focus, then anything due today or overdue — to send to tomorrow, next week, the wishlist or done, and up to three picks for tomorrow's focus, with today's unfinished focus kept by default. Routine ticks and the journal line save as you make them; *Close the day* applies the rest with one Undo, which also reopens the day.
- **Home → Today: Habits** — things you do most days. Add one with a name, an emoji and the weekdays it is due (none chosen means every day); tick it for today and the ring fills in its colour; the streak shows as 🔥 n. A weekday habit reads *Rest day* at the weekend and its streak survives it — days it is not due on are skipped, not counted as misses, and an as-yet unticked today never zeroes a run. Tap the name to rename, reschedule or delete (two-step, with undo). Habits are personal, like the journal.
- **Home → Today: Routines** — short checklists you run at a time of day: morning, evening or anytime. Ticks belong to the day, so every routine starts fresh tomorrow without anything to reset. The card shows the routines for this time of day, with *Show all* for the rest; add, edit (a step you move keeps its ticks; a reworded step starts unticked, and the others keep theirs) and two-step delete with undo.
- **Home → Week** — the weekly (or monthly) review, opening with *You said* — last week's (or month's) Top 3 and reflections, to tick what you kept — then what got done (with a per-day chart), what slipped (push everything overdue to Monday, or send it back to the wishlist, in one click), what's already planned next, people seen, where you went, what you wrote in the journal, **habit consistency** (done of due per habit and overall, counted from the day each habit was created and only up to today), project movement and stalled projects, spend. Write your Top 3 and reflections, then ✨ write my summary drafts an honest review from the data — journal, habits and the Top 3 you kept included. (Sunday's automatic draft in the digest reads the journal but does not count habits yet.)
- **Home → Week: Plan next week** — on the Week toolbar (the main button from Friday to Sunday), on Today on a Sunday (on the review card, or on This week's 3 when there is no review yet) and from the palette, **Plan next week** proposes the week ahead as rows to tick: dinners for the empty nights (*Swap* for another, or *Pick…* any recipe or a place to eat out; a busy night starts unticked), catch-ups with people who are due one, on a day you choose, overdue tasks moved to a day of that week or back to the wishlist, the bills falling due (listed, not ticked), and, while last week's review has no Top 3, a Top 3 that Today then shows as this week's 3. ✨ *Polish with the assistant* can suggest dinners and catch-up ideas. Nothing is added until *Add n to next week*, and one Undo takes it all back; a row you untick is left out of that week's next proposal.
- **Home → Journal** — also a card on Today: one entry a day in your own words, with an optional mood (five faces). It saves as you type. Tag who the day was about with "+ Who" and their faces sit on the entry; a person's card on People shows how often they appear in your journal, separately from visits. Today shows yesterday's line and your streak; the journal page lists every day with search and inline editing, with a streak, the days written this month, a 30-day mood average, a mood chart (one column a day, a weekly average per week) over the last 12 weeks — 6 on a narrow screen such as a phone, where the stats sit behind *Show stats* — and, once 14 days in the last 26 weeks have a mood, the average mood for each weekday over those weeks with the lowest named. Sunday's digest reads the week's entries when it drafts the review if you let it (Settings → Reminders, off by default). On a phone, `drafter://journal?text=…` offers a line from any Shortcut: the journal opens with the text shown, and it is appended only when you press Add.
- **Tasks → List** — searchable, filterable, sortable list of everything, plus JSON backup/export, "Log something done", the Trash, and undo-able deletes. It opens on open tasks (choose *All statuses* or *Done* for finished ones) and shows the first 200, with *Show all* for the rest.
- **Tasks → Board** — kanban by status. Drag cards between columns (or use the ⇄ picker on touch); every move offers Undo in the toast, which also takes back a repeat it spawned. Dropping into Done stamps the completion date and spawns the next occurrence of a repeating task. Done shows the 30 most recently finished (the rest are on the list), and *+ Add* under a column starts a task in that status.
- **Tasks → Bills** — a month of payments at a time, with ‹ and › to step through the months: overdue, still to come, paid, and what an average month costs (see Bills below). Each bill still to pay has a **Paid** button that marks it done; the undo in its toast puts the bill back and removes the next copy a repeating bill made.
- **Tasks → Notes** — your notes and every project notepad that has something in it (archived projects are left out) in one searchable list, pinned notes first; open one to write in it (rich text with inline photos), and *All notes* returns to the list. An empty notepad opens from *Open the notepad* in the project editor. The ☐ Task button turns the selected line into a task.
- **Calendar → Month** — month view by due date (done tasks show on their completion day), with birthdays, anniversaries, project milestones and targets beside events and meals. Click a day to open it: everything on that day, its meals, and buttons for a new task, a new event or the work day. Drag a task pill to move its due date. A future event from a subscribed calendar offers *Plan for this*, a prep task due the morning before.
- **Calendar → Week** — the week as a list, with each day's tasks, events, meals, birthdays, anniversaries, milestones and work-day badge, and a **+** per day. Tap a day's header to open it, or drag a task to another day to move its due date.
- **Calendar → Timeline** — from the day your account began to today, fitted to the width of the window while it fits (a longer history scrolls sideways and opens at today): projects as bars across months (dashed when the span is inferred — set start/target dates to pin it), milestones as ◆, due tasks as dots, a today line. Click anything to open it.
- **People** — the people you want to keep close. Give each a rhythm ("every 2 weeks"); any completed task they're attached to counts as seeing them, or log a visit in one tap. Each person is a row showing last seen, the days you saw them in the last 30/90 days and a status — on track, due a catch-up, overdue, or *No visits yet* — that opens for the average gap between those days, a 12-week sparkline of days seen and the rest; several events with someone on one day count as one day seen, and the events show beside the days wherever the two differ (a row, *all time*, the Week review). Filter by group (Family, Friends, Other), search, and sort by who needs attention, by name, or by when you last saw them, with tiles counting days together, occasions, people seen, and who is overdue or due a catch-up. Today surfaces the ones that need attention with **Plan something** or **Saw them**. People also carry a birthday and anniversary: Today lists them three weeks out with **Plan a gift** (a task due five days before, seeded with their notes), and the calendar's day sheet offers the same on the day itself; once a gift task is open, both say *Gift planned* and open that task rather than starting a second. On a past event from a subscribed calendar (one made in Drafter offers *Edit* instead), **Who was there?** lets you tick who came, or type a name not yet in People, which saves and ticks them, and logs a visit for each; it matches the event's location to a saved place (or saves it as one) so the outing lands there too. The **year with people** table counts days seen per month per person, with each year's total days and total events and a drifting/more-lately trend by days. Each person's card lists **where we go** together, and ✨ Ideas draws on those places and on favourites you haven't taken them to yet. **People → Places** is a segment on the same tab: restaurants, fast food, cafés, bars, outdoors, venues, shops, home and other. Attach a place on a task or log an outing; the list shows when you last went, how often, how many of those were meals you ate there, and who you usually go with, and ✨ **Where should we go?** suggests outings from your own favourites and the places you've drifted from — tap one to plan it. Give a place a return rhythm and Today and the morning digest say when it's been a while.
- **Kitchen** — recipes with ingredients and steps, a week of breakfast, lunch and dinner slots, and a grocery list built from whatever is planned (duplicate lines merge; Have / Need / Got it). Cook mode walks the steps and keeps the screen awake. Tonight's dinner also shows on Today. The Cook menu starts with **Something new…**: name a dish you are cooking for the first time and it is planned straight away, saved as a recipe with just its name, ready for ingredients and steps on the Kitchen tab. A slot can also be a night you **eat out** rather than cook: pick a saved place from the same menu the recipes are in, or **Somewhere new…** to name it on the spot — that saves the place as you plan the meal, so a first visit starts being tracked without a trip to Places. In both menus, typing a name you already have reuses it rather than making a second copy. "Out, no place" records a bought meal without naming where. A bought meal adds nothing to the grocery list, and once its day has passed it counts as an outing at that place — so the place's card says how often you ate there, and a restaurant you ordered from last night stops nagging you that it's been a while. **Every planned meal, cooked or bought, shows on the calendar** in both the month and week grids, so what you're eating sits beside the rest of the week; cooked nights are orange, nights out are blue. You can plan them there too: the **+** on a week day asks Task, Meal, Event or Work day, and any day you open lists breakfast, lunch and dinner with the same picker the Kitchen tab uses. Planning from either place rebuilds that week's grocery list. A line you tick stays where it is, struck through, so the list never jumps under your thumb mid-shop and a mis-tap is one tap to undo; *Clear ticked* tidies the list when you are done. A line added by mistake comes off the list with its ✕ (two steps); it stays off when the list is rebuilt, until a newly planned recipe needs it, and *Removed (n)* at the foot restores it. On This week, while any dinner from today on is still empty and you have a recipe or a place saved, **Plan this week's meals** is offered: favourites you haven't had lately, each with its reason, a Swap for each night and *Pick…* to choose your own recipe or place, lunches too if you want them, and ✨ *Ask for ideas* when nothing appeals. A night with an event across the dinner hour, from your own events or a subscribed calendar, is marked busy and starts unticked; only the ticked nights are planned, all at once with one undo. ✨ **Suggest recipes** reads the recipes you cook and offers dishes like them — *Recipes you might like* — to add to your recipes or delete for good. Suggestions waiting and the titles you delete are kept on this device only, so another device keeps its own list; *Accept* saves the dish with its drafted ingredients and steps and opens it.

The task editor's ✨ buttons break a task into checklist steps and suggest tags, and under the description ✨ Clarify, ✨ Add details and ✨ Summarize each propose a rewrite that you can use in place of yours, add below it, or discard. Pasting or sharing a sentence fills the same fields as typing it into the palette, and a URL goes into the description, where every link other than the GitHub card's shows under the text as a chip that opens in a new tab (Safari's sheet on the phone).

## GitHub links and write-back

Paste a GitHub URL into a task's description, or a project's **GitHub** field — an issue, pull request, repository, or a Projects (v2) board like `https://github.com/users/you/projects/3` — and the editor shows a live card (for a task, from the first GitHub URL in its description, which saving links): title, open/closed/merged/draft state, labels, assignees, comment count, last update. The lookup goes through the session-gated `/api/github` function. Public issues and repos work without configuration; set `GITHUB_TOKEN` on Netlify (a fine-grained PAT with read access to the repos, plus `read:project` for Projects boards) for private repos, Projects, and a far higher rate limit. With `GITHUB_TOKEN` granted write access, the card gains **Close issue on GitHub / Reopen**, marking a task with a linked issue done closes the issue, and a task in a project that links a repo can **Create a GitHub issue** from its title and description.

**Two-way Projects sync.** When a project's GitHub field holds a Projects (v2) board, the project editor offers **Sync status and due dates**. Turning it on reads the board's fields and proposes a column for each Drafter status (Wishlist, To do, Doing, Done), matched by name or a common alias such as In progress or Shipped, which you can change per row; you can also pick which single-select field counts as Status. Due dates stay out of it until you choose one of the board's date fields under *Write due dates into*. After that it runs both ways: moving a task here writes its column (and its due date, when it has one that changed) onto the board row of its linked issue or pull request, debounced so dragging a card across the board is one write, and clearing a task's due date leaves the board's date as it is; and on focus and every 30 minutes each synced board is read back, so a card someone moved on GitHub moves the task here, with a toast and an undo. The newer edit always wins — a board row is only honoured when GitHub touched it after the task's own `updatedAt` — and a board row with no date is never read as "clear the due date". Only tasks in the project that holds the board take part. The board is read up to its first 300 rows; when it has more, a toast says so once a session. When more than one task links the same issue — a repeating task's next occurrence, or a duplicate — a move on the board changes none of them until the others are unlinked or in the Trash. Failures are silent by design: GitHub being unreachable must never block a local edit. This needs `GITHUB_TOKEN` to carry the `project` scope (read **and** write); without it the toggle shows exactly that, and nothing else changes.

**Events.** A task marks a moment; an **event** blocks a slot. Add one from the calendar's **+** (or a day's *New event*) with a real start and end, or all day, plus a location and notes. They render in the month grid, the week list and the day sheet in their own colour, alongside tasks and meals, and open again for editing from the day sheet. Events are stored like everything else, so they sync, appear in Trash and survive offline. They also go **out**: every event rides the Drafter ICS feed with its true duration, so a subscribed calendar shows the slot as busy, and it is written straight into your real calendars as a busy block: the Google **Drafter** calendar when Google mirroring is on, and the **Drafter** calendar of *every* Microsoft account you have mirroring enabled for. Unlike a mirrored task, which shows as free time, an event shows as busy — blocking time is the point. Deleting one removes it from those calendars too, and Undo puts it back on them. Changes come back as well: move an event, make it all day or rename it in Google or Outlook and Drafter takes the change on the next pull, as long as it is newer than your last edit here, with a toast saying how many were updated. Notes and location keep Drafter's copy, and deleting the event there leaves it in Drafter.

**Work days.** Mark where you are working and your hours: a **work day** is set to 🏠 Home or 🏢 Office with a start and an end, from the calendar's **+** (*Work day*), a day's *Set work day*, or the event editor's *Work day* switch. Pick weekdays under *Repeat on* (Monday and Friday at home, say) and a number of weeks, and each of those days is created separately, so any one of them can be changed on its own — the Friday you go in instead. A work day is a property of the day rather than something happening on it, so it shows as a small green 🏠 Home or blue 🏢 Office badge with the hours in am/pm (9am–5:30pm) on the month cell, the week header and the day sheet, and it is left out of the day's item count. Today's briefing strip shows the same mode and hours. It is never busy time: Google gets it as free, Outlook as **working elsewhere** (home) or free (office), and the ICS feed marks it transparent, so it never blocks anyone booking you during your working day.

**Bills.** Track what the household pays: bills, credit cards, subscriptions, loans. A bill is a task with an amount, so tick *This is a bill or payment* in any task (or press **+ Bill** on Tasks → Bills, or *New bill* in the command palette, which starts one repeating monthly), choose its kind, who is paid and whether it is paid automatically, and set the **Amount due**. It then sits on its due date in the calendar as 🧾, 💳, 🔁 or 🏦 with its amount, reminds you like any task, shows on Today, and repeats monthly, quarterly or yearly. A bill falls due on its own day however early or late you paid it, and one due on the 31st goes 31 Jan → 28 Feb → 31 Mar rather than settling on the 28th. Marking it done with nothing under **Paid** records the amount due as paid. The **Bills** segment of the Tasks tab shows a month at a time: what is overdue, what is still to come, what has been paid, and what an average month costs across every repeating payment. Amounts appear only inside Drafter: the Google and Outlook mirrors and the ICS feed never send one. They do send the title, the description, the project, the status and the priority, so a figure typed into the title or the description goes with them. Figures are shown in pounds.

## Backups

**JSON backup:** Tasks → Export JSON / Import JSON. Re-importing is last-write-wins by `updatedAt`. "Log something done" is still on the Tasks toolbar for recording something after the fact.

## Calendar sync

All integration secrets are **per user**: each signed-in account's Google tokens and feed link live in its own `user_settings` row, readable only by the Netlify functions (service role, no RLS policies). A browser session never sees a token, and no user can reach another user's calendars. `SUPABASE_SERVICE_KEY` on Netlify is what enables this table.

- **Google Calendar (OAuth).** Settings → Calendars → *Connect Google Calendar*. Tick the calendars to show (birthdays, family, holidays…) and they overlay the Month view (dashed pills), the Timeline (a Calendar row), and Today's *Coming up* list, each with a **Plan** button that creates a prep task due the morning before. Turn on *Mirror my tasks* and open tasks with due dates are written into a "Drafter" calendar in your Google account within seconds of a change (updated as they move, removed when done). Google → Drafter is read-only for your own calendars; the mirror is two-way for mirrored tasks: drag one in Google Calendar and its due date moves here on the next pull (on focus and every 30 minutes); delete one there and the task is marked done here, with Undo in the toast. Setup, once per deployment: Google Cloud Console → create a project → *APIs & Services → Library* → enable **Google Calendar API** → *OAuth consent screen* (External; add yourself as a test user, then **publish** the app — while it stays in *Testing*, Google expires refresh tokens after 7 days) → *Credentials → OAuth client ID → Web application* with the authorized redirect URI `https://<your-site>/api/google/callback` → set `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` on Netlify and redeploy.
- **Outlook / Microsoft 365 (OAuth).** Settings → Calendars → *Connect Outlook*. Personal and work accounts can both be connected at once — add the second with *Connect another account*. Tick the calendars to show and they overlay the Month view, Timeline and Today exactly like Google's. Turn on *Mirror my tasks* per account and open, dated tasks are written into a "Drafter" calendar there; moving one in Outlook moves its due date back here, and deleting one marks the task done, with Undo in the toast. Outlook's deletions are found when the calendar is read back, at most every 15 minutes, and if many vanish at once (the calendar emptied or swapped) they are written back instead of being marked done. Setup, once per deployment: [Azure Portal](https://portal.azure.com) → *App registrations* → *New registration* → supported account types **Accounts in any organizational directory and personal Microsoft accounts** → redirect URI (Web) `https://<your-site>/api/microsoft/callback` → copy the Application (client) ID, then *Certificates & secrets* → *New client secret* → set `MICROSOFT_CLIENT_ID` and `MICROSOFT_CLIENT_SECRET` on Netlify and redeploy. Recurring events are expanded by Microsoft, so birthdays and weekly meetings arrive as real occurrences.
- **Any other calendar (iCloud, holidays, a .ics link).** Settings → Calendars: paste an ICS address (an iCloud *Public Calendar* webcal link, Google's *Secret address in iCal format* if you'd rather not use OAuth, a holidays feed). Same overlay, read-only, fetched through the session-gated `/api/calendars` function (calendar hosts don't send CORS headers) and cached in IndexedDB. Recurrence (birthdays, weekly classes, monthly bills), EXDATE and detached overrides are expanded server-side by `shared/ics.mjs`. Up to 12 calendars — Google, Outlook and .ics together — are shown at once; one past that says so in Settings until another is unticked. A feed over 4 MB is refused, and events are read from 60 days back to 400 days ahead.
- **Email in.** Settings → *Create my email-in address* gives a private webhook URL; point Mailgun Routes, SendGrid Inbound Parse, Cloudflare Email Workers, Zapier or Make at it and a forwarded email becomes a task tagged *email*: the subject, without Re: or Fwd:, is the title, and the body, the first link and the sender all show in its description. When the site has an AI key, a second pass then tidies the title and adds a due date, priority and tags taken from the message; if the model is slow, the task is kept as it arrived. *Reset* gives a new address and *Turn off* stops it.
- **Subscribe link (Apple Calendar and others).** Settings → *Create my subscribe link* gives a private `/api/feed.ics?token=…` address for your account: your open tasks with due dates, dated tasks done in the last 30 days (with a ✓), project targets and milestones, and your events and work days, as an iCalendar feed. Subscribe once in Apple Calendar (*File → New Calendar Subscription*) or Google (*Other calendars → From URL*); reset or turn the link off any time. Apple refreshes as often as you configure, Google every several hours (which is why Google gets the OAuth mirror instead).

In a household the mirrors and the subscribe link carry only your own things: tasks assigned to you, unassigned tasks of your own, and your own events and work days; the subscribe link also carries the dates of your own projects. A household member's tasks and events stay out of your calendars, though you see them here. Reconnecting an account finds the Drafter calendar already there rather than making a second one. If you delete the Drafter calendar in Google or Outlook, a new one is made and everything is written into it again, and Settings → Calendars says so beside the mirror switch until you dismiss it. Drafter's own calendar is not offered as an overlay, since it would show every entry twice; one ticked before stays listed so it can be unticked.

## Reminders, backup, PWA

- **Push reminders (app closed):** Settings → Reminders → *Enable on this device*. An hourly scheduled function sends a morning digest at your chosen local hour (today's focus, overdue, due today, occasions, people due a catch-up, places you set a rhythm for that are well overdue, tonight's dinner, and on a Sunday a *Plan next week* line when there is something to plan) and a nudge when a timed task comes due (hourly granularity). Tapping the digest opens Plan my day, or on a Sunday the Week review, with Plan next week over it when there is something to plan. Optionally the digest goes by email too, with the same link, labelled *Plan your day*, or *Plan the week* on a Sunday when there is something to plan. On Sunday the digest also drafts your weekly review; tick *Let Sunday's draft read my journal* in Settings → Reminders if the week's entries should inform it (off by default — the ✨ summary you press for on Home → Week always may).

- **No backup file:** nothing is written to a file automatically — the synced database is the durable copy, and the server snapshots below back it up. For a file of your own, use Tasks → Export JSON (see Backups).
- **Server snapshots (owner only):** a daily scheduled function writes one JSON snapshot per account into the private `media` bucket at `backups/<user id>/<date>.json`, keeps the newest 14, and purges version history past 60 days and purged tombstones past 90. Admin → **Backups** lists what is actually there with sizes and a five-minute signed download, and *Back up now* runs the identical pass on demand — so a schedule that has never fired is visible instead of assumed.
- **Is my data still there? (owner only):** Admin → **Data** counts live records by kind, tombstones, unowned legacy rows, `posts_history` versions, rows per account and the newest server sync — straight through the service key, so it bypasses every policy and shows what the database really holds. Admin → **Integrations** goes further than "configured": it makes a real AI call, sends a real test push to this account's devices, and previews or sends your own digest. Admin → Data also shows a **Sync check**: every hour the digest writes one test row of each kind through the same server call the app syncs with and rolls it back, so nothing is kept, and the card says whether the server accepted all of them and when, or which kinds it refused and since when, with *Check now* beside it. If a kind is refused, the owner is told through the digest's push or email, at most every 12 hours.
- **PWA:** the production build is installable and works offline.

## iOS app

The same app, in a native shell (Capacitor). Nothing is duplicated: the web
bundle is packaged into `ios/`, talks to the hosted API and Supabase exactly
as the browser does, and syncs through the same `sync_posts` round-trip.

```bash
npm run ios          # builds the bundle for the app, syncs it, opens Xcode
```

Then run on a simulator or a phone from Xcode. `npm run build:ios` alone
rebuilds and syncs without opening Xcode. To preview the native look without
a device build, open the web app with `?native=1`: that stamps `html.native`
the way the shell does, so the iOS layer renders in a browser. The installed app does **not**
pick up a web deploy by itself — run `npm run ios` (or `build:ios` then
Xcode) after native or plugin changes. A free Apple ID installs on your own
iPhone for a week at a time; a paid developer account is needed for
TestFlight, the App Store, push through Apple, widgets, a share extension
and associated domains. This project currently ships the unpaid path.

What the shell adds over the installed web app:

- **Native patterns.** The same five tabs, but iOS large titles, editors as
  card sheets with a grab handle, the segment rows as real iOS segmented
  controls (a filled track with a raised thumb), native touch feedback and
  a frosted tab bar. **Pull to refresh**: drag down from the top of any tab
  and let go to refresh — items, calendars and the briefing, the same refresh
  the app runs when it comes back to the foreground. Gated on `html.native`,
  so the web build is untouched.
- **Reminders with nothing to set up.** Settings → Reminders → *Remind me on
  this iPhone* schedules a notification on the phone itself at each task's due

## Data & sync model

Tasks, projects, notes, people, places, recipes, meals, groceries, events, habits, routines, journal entries, calendars, reviews and templates cache locally in IndexedDB (validated and migrated on load) and sync to Postgres with **delta sync**: only dirty ids push, and only records newer than the last `synced_at` cursor move back. The table is still called `posts`; each row's type is `data->>'kind'`. **Pre-v3 rows are never rewritten** — every reader (the app, the MCP server) converts a legacy post into a task on read, so the upgrade needs no data migration, only `supabase db push` for new generated columns and the wider kind/status validation. A new kind must be added to the `sync_posts` allow-list **before** clients write it, or the server rejects the row. A row the server refuses is never dropped, whatever its kind: it stays waiting on this device, still counts in the sync pill, is tried again with a growing wait (30 seconds, doubling up to 30 minutes) and is listed in Settings → Data → Sync under *Couldn't sync (n)*, with *Try again* and a two-step *Discard my copy*. Habits, routines, the journal, reviews and calendars are personal; everything else is shared with the household. Sync also fires when the app returns to the foreground, and saves and pushes at once when it goes to the background — a hidden tab, a closed page or the iPhone app sent away — so an edit made just before switching away is not lost if the system then closes the app. Last-write-wins per post by `updatedAt` is **enforced by a database trigger** for every writer (app, MCP, raw REST), with strictly-increasing stamps on every edit. Before pushing an edit of a record the server already had, the app pulls first and merges the two edits field by field against the last copy the server confirmed: a title changed on the phone and a checklist line ticked on the laptop both survive, and checklist lines, comments and grocery lines merge item by item. Only when both changed the same field does the other device's value stand, and a toast says so (*"Buy paint" changed on another device too — kept the newer edit*) with **Keep mine** to put yours back. A push that loses last-write-wins is kept in `posts_history` as a lost version rather than thrown away, and the winning copy comes back to the device whatever the cursor. Deletes are tombstones: a deleted record stays in Trash for 90 days, restorable on every device, and then devices drop it from their cache; the server keeps the tombstone. *Delete forever* replaces the record with a content-free tombstone, which the server hard-deletes after 90 days and records in `purged_ids`, so a device that later pushes an old copy is told the id is `gone` and drops it, unless the record was created after the purge (a re-planned meal slot, say). Images upload to Supabase Storage, where you and anyone in your household can read them, with IndexedDB as the offline cache, so they follow you across devices.

## Development

```bash
npm test             # vitest
npm run lint         # eslint over src, netlify/functions, mcp, shared and scripts, --max-warnings 0
npm run check        # lint + tests + both type-checks + production build + precache check (what Netlify runs)
npm run db:smoke     # throwaway Postgres: apply every migration, exercise sync_posts and the policies
npm run mcp:smoke    # ...and drive the real MCP server process against it, end to end
```

`check` type-checks twice: the app with `tsc --noEmit`, and the server code (Netlify functions, `mcp/`, `shared/` and `scripts/`) with `tsc -p tsconfig.server.json`, which reads that JavaScript through its `.d.mts` declarations. It ends with `scripts/check-precache.mjs`, which fails the build if any file in `dist/assets` is missing from the service worker's precache, so the installed app can never go offline without part of itself.

`db:smoke` needs the PostgreSQL binaries on PATH (`brew install postgresql@17`). It stubs what Supabase provides (auth, storage, roles), applies `supabase/migrations` in order, then writes every record kind as a signed-in user, checks a household peer sees shared kinds (notes and events included) but not the owner's journal, review, calendar, habits or routines, nor their history, and cannot write over the owner's journal or routines; that the service role writes as the owner; that last-write-wins holds and a losing push is kept as a lost version; that history is kept and scoped; that a purge tombstone is accepted and a purged id stays gone; that deleting an account hands shared rows to the heir; that the sync canary passes every kind; and that the agent-access tables and functions are closed to signed-in clients. Run it after any migration: a function can compile and still reject every write.

`mcp:smoke` starts the same throwaway database (both share the boot-and-migrate loop in `scripts/lib/pgtest.sh`), serves a minimal PostgREST shim over it that translates the handful of requests `mcp/server.mjs` makes into SQL — and answers **501 with the path** for anything else, so an unimplemented request can never look like an empty result — then spawns `node mcp/server.mjs` and speaks JSON-RPC to it over stdio. Projects, tasks, recurrence, today's focus, notes, visits, places, meals, groceries and the journal are each written through a real tool call and then read back straight from Postgres, with the legacy bare-array RPC shape and a rejected id covered too. It then serves the hosted endpoint and checks each way in — an agent token over HTTP, the stdio proxy and an OAuth connection — for whose rows it can reach. Neither smoke test is part of `npm run check`: Netlify has no Postgres.

## AI agents

Drafter is an MCP server: 28 tools that cover the whole planner and write through the same merge-safe RPC as the app — projects and tasks (with today's focus), notes, people and places, the kitchen, the journal, the Today overview, and a read-only proposal for next week. It runs hosted at `/api/mcp` (stateless JSON-RPC over HTTP). Add Claude as a custom connector with that URL and approve it on Drafter's consent screen (OAuth 2.1 with PKCE and dynamic client registration), or create a token in Settings → Assistants (shown once; it can always read, and you tick whether it can add and change things and whether it can read and write your journal). Claude Code and any client that sends a header use the token straight against `/api/mcp`, and the page gives the `claude mcp add --transport http` command; for anything that launches a local process, `mcp/server.mjs` with `DRAFTER_AGENT_TOKEN` set forwards stdio to the hosted endpoint. Every call through `/api/mcp` runs as the signed-in user under the database's row policies, a connection sees only the tools its scopes allow (read, write, journal), and Settings → Assistants lists every connection and revokes any of them. The rules an agent needs — week keys, grocery merging, place matching, journal appends, the week plan — live in `shared/*.mjs` and are the same code the app runs. Registration details and the raw HTTP alternative are in the local, unpublished `BOTS.md`.

The hosted server needs `SUPABASE_SERVICE_KEY` on Netlify (with the project URL and anon key) and the agent-access migration applied; until then `/api/mcp`, `/api/agents` and the OAuth endpoints answer 501. Optional: `MCP_RATE_LIMIT_PER_MIN` (calls a minute per connection, 60 by default) and `OAUTH_REDIRECT_ALLOWLIST` (the hosts an assistant may be sent back to; claude.ai, claude.com, localhost and 127.0.0.1 by default). A new OAuth connection can read and change things, and reaches the journal only if you tick it. `mcp/server.mjs` still has a deprecated mode: started with `SUPABASE_URL` and `SUPABASE_SERVICE_KEY` and no token, it runs every tool itself with the service key, which reads every account, and warns on stderr. Use a token instead.
